## 1. 审查结论

**项目已有适合本人和少数熟悉房东使用的业务基础，建议下一阶段优先收口可靠性、备份恢复和发布验证，再继续扩大功能与使用范围。**

账单归属、台账模块权限、收款幂等、冲销留痕和不可变单据归档已有实质实现；现有后端和客户端测试也覆盖了不少异常路径。因此，没有依据建议推倒重写或立即更换技术栈。

本轮发现的主要短板集中在基础保护与交付流程：

- 数据库配置的实际效果与代码意图不一致。
- 日常数据库备份不能独立恢复磁盘上的合同附件和照片。
- 同版本号构建缺少提交指纹，升级前快照可能跳过真正的新构建。
- 多个业务上传入口缺少解析前的请求总量限制。
- 默认代理信任、批量上传失败语义和自动验证入口仍有缺口。

这些问题不能被“现有测试全部通过”抵消。本报告共列出 **8 项问题：4 项 P1、4 项 P2**；其中 P1 表示建议在下一次相关发布或扩大使用前完成处理，并不表示已经观察到生产事故。

### R01：SQLite 连接参数与实际驱动不匹配

**位置：** [database.go](../server/database/database.go):147–176，`server/go.mod` 中实际使用 `gorm.io/driver/sqlite` 与 `github.com/mattn/go-sqlite3 v1.14.22`。

当前 DSN 使用 `_pragma=journal_mode(WAL)` 等参数。实际驱动源码解析的是 `_journal_mode`、`_foreign_keys`、`_synchronous`、`_busy_timeout` 等专用键。对实际 `database.InitDB` 建立的新库观测如下：

| 检查 | 当前参数，两次一致 | 驱动支持参数，两次一致 |
|---|---|---|
| `journal_mode` | `delete` | `wal` |
| `foreign_keys` | `0` | `1` |
| 明确建有外键的合成表插入孤儿行 | 成功 | 被拒绝 |
| `busy_timeout` | `5000` | `5000` |
| `synchronous` | `1` | `1` |

后两项读数一致，不能据此认定现有 `_pragma` 参数有效；本轮确认偏离意图的是 WAL 与外键开关。外键示例使用专门建立的合成表，不代表已经发现真实业务孤儿记录，也不表示所有业务关联都声明了数据库外键。

**影响：** 代码注释和运行假设不一致；新库并未获得声称的 WAL 行为，已声明外键的约束也可能不执行。已有库的日志模式还可能受历史持久化状态影响，本轮未读取生产 PRAGMA。

**建议：** 改用当前驱动支持的 DSN，并在初始化后回读关键值。变更前在生产脱敏副本检查实际外键定义与 `foreign_key_check`，验证迁移和删除流程；不能直接把开关打开就宣称历史数据已修复。

**完成标准：** 新建库、重开连接、旧库迁移副本和 Linux 镜像均验证期望 PRAGMA；有外键的非法写入被拒绝；业务回归通过，异常启动给出可定位信息。

### R02：数据库备份与完整灾备的边界不清

**位置：** [backup.go](../server/backup/backup.go):53、139；[export.go](../server/rental/export.go):116；[attachments.go](../server/rental/attachments.go):93；[AdminBackupView.vue](../web/src/views/AdminBackupView.vue):11–17。

日常备份和定时导出都是 `VACUUM INTO` 生成的 `.db`。上传的合同、租客附件、房源/抄表照片等另存磁盘，库中保存路径。备份页面却将下载后上传 `.db` 描述为换机和异地容灾途径，没有同时说明这些文件必须另行保存。

**影响：** 仅带 `.db` 在空白机器恢复，可以恢复附件记录，却无法恢复对应文件；原机器上的附件被删除后，恢复旧数据库也不能重建已删文件。服务端生成并存入 `issued_documents` 的 PDF 属于数据库内容，应与上传附件区别说明。

**已有缓解：** `deploy/release.py:146` 在发布时复制整个数据目录，因此不能说“项目所有备份都漏附件”。但发布前整目录备份不等同于日常完整灾备；本轮也未核查是否另有生产异地备份。

**建议：** 先纠正页面和运行文档中的恢复边界；制定包含数据库一致性快照、所有文件目录、必要配置及清单校验的完整备份方案。异地副本应限制访问，明确备份间隔、保留数量和恢复步骤。

**完成标准：** 在空白隔离目录恢复一组包含上传合同、身份证合成图、抄表照片和已生成收据的样本；核对记录数、文件哈希、鉴权下载与 PDF 打开，并记录可接受的数据丢失窗口和恢复耗时。

### R03：构建身份没有进入升级快照判据

**位置：** [deploy/Dockerfile](../deploy/Dockerfile):8；[version.go](../server/version/version.go):9–11；[server.go](../server/server/server.go):53–97、159。

云镜像只注入 `Version` 和 `AppName`，`BuildTime`、`GitCommit` 保持 `unknown`。`binaryFingerprint()` 恰好使用这三个字段判断是否为已经处理过的版本。因此，多次以 `0.10.0` 构建时，程序内指纹都是 `0.10.0|unknown|unknown`。镜像外部 revision 标签不会自动改变这些程序字段。

**复现：** 用当前构建参数运行探针，版本字段均为预期缺失状态；对实际 `preUpgradeSnapshot` 调用，第一次创建快照，第二次相同元数据返回“本版本已快照过”；仅给提交字段设定新的合成值，控制组便再次创建快照。

**影响：** 以后同版本号交付数据库变更时，启动快照可能被跳过。程序还会在快照创建失败后继续迁移；这属于同一恢复保护链需要一并决策的行为。发布脚本的停机备份能够缓解部分场景，但不能证明所有启动方式都受其保护。

**建议：** 将完整 commit 和构建时间注入二进制，核对 `/api/version` 与制品清单一致；明确快照失败时迁移应中止，或仅在已验证外部备份且明确选择降级时继续。

**完成标准：** 同版本、不同提交的新构建会触发快照；同一构建重启不重复创建；快照不可写时遵守约定的失败策略；迁移后验证原版本兼容性，而不是通过覆盖旧数据库回退业务。

### R04：业务文件上传缺少解析前总量限制

**位置：** [attachments.go](../server/rental/attachments.go):220；[contracts.go](../server/rental/contracts.go):221；[room_photos.go](../server/rental/room_photos.go):111；[meter_photos.go](../server/rental/meter_photos.go):141；[applications.go](../server/rental/applications.go):549；[tenant_change.go](../server/rental/tenant_change.go):96。

这些路径在 `MultipartForm()` 解析之后才校验单文件大小或张数。全局 `LimitJSONBody` 只保护 JSON，不约束 multipart。当前 Gin 源码中该方法调用 `ParseMultipartForm`；内存阈值不等于整个请求的接收上限。

**影响：** 即使最终拒绝，过量文件内容也可能已经消耗内存或临时磁盘；容器 `/tmp` 仅配置 256 MiB，而且 PDF 转换也使用临时目录。合法房东上传，以及持有效登记链接提交申请，都存在相应入口；不是宣称任何匿名请求都可直接操作所有上传 API。

**证据边界：** 本轮确认了代码缺少前置总量限制，未向生产发送大文件，也未通过耗尽本机磁盘做拒绝服务实演。

**建议：** 在首次解析前按接口设置 `http.MaxBytesReader`；明确整请求、文件数量、单文件和表单字段上限。有效的大批次也要结合 256 MiB 临时空间控制并发。可参考已有 `server/rental/backup_upload.go:81` 的前置限制形式。

**完成标准：** 超限请求尽早返回明确错误；覆盖未知长度/分块请求、多个文件叠加、未使用字段夹带文件和中途断开；确认临时文件可回收，并验证上传与 PDF 并发时其他请求仍可响应。

### R05：代理信任没有显式配置

**位置：** [server.go](../server/server/server.go):354；[ratelimit.go](../server/middleware/ratelimit.go):71。

仓库没有调用 `SetTrustedProxies`；实际 Gin v1.12.0 默认信任全部代理地址，而限流和请求日志依赖 `ClientIP()`。

**复现：** 同一 `RemoteAddr`、限额设为每分钟 1 次，依次发送相同、相同、变化的 `X-Forwarded-For`：默认配置得到 `200、429、200`；关闭代理信任的对照组得到 `200、429、429`。

**影响：** 直连应用时可伪造来源切换限流桶，也会影响来源日志可信度。生产 Compose 仅映射回环地址，是已有缓解；公网是否仍可利用取决于实际 Caddy 转发头处理，本轮未验证，不能写成已经确认的公网攻击。

**建议：** 直连模式关闭代理信任；反向代理部署显式配置实际可信跳点，结合容器网络确认远端地址，不能机械假定容器里看到的总是 `127.0.0.1`。NAS 网关仍按既有独立身份标记处理。

**完成标准：** 直连、Caddy 转发及适用的网关入口分别验证来源、伪造头和限流；真实不同用户不被错误合并到同一桶。

### R06：批量附件返回失败却已经保存部分文件

**位置：** [attachments.go](../server/rental/attachments.go):253–309。

处理逻辑逐文件校验并立即落盘、插入记录。若第一个 PDF 合法、第二个文件类型不允许，会在第二个文件返回 400，但第一个已经保存。

**复现：** 使用实际路由和新合成租客，按确定顺序上传“有效 PDF＋无效文本”两次；两次均返回 400，数据库最终存在 2 条已保存附件。

**完成标准：** 覆盖第二个文件非法、磁盘写失败、数据库插入失败和响应丢失；检查记录和实际文件的一致性。相同失败批次重试不产生未告知的重复附件。合同、照片等类似循环另做针对性检查，本轮未逐一复现它们。

### R08：本地验证包装器在 PowerShell 5.1 下误报失败

**位置：** [verify.ps1](../scripts/verify.ps1):24。

脚本设定 `$ErrorActionPreference='Stop'`，将 Python 的 stderr 合并后传给 `Tee-Object`。Python unittest 正常进度写在 stderr；本机 PowerShell 5.1 将这类输出转成 `NativeCommandError`。

**复现：** 相同 8 项发布测试由 Python 子进程直接收集输出时通过；用原脚本相同的管道形式运行则进入异常分支，包装进程退出 1。项目发布记录已有此类现象，但当前根门禁仍保留该形式。

**建议：** 复用 `verify-miniprogram.ps1` 已采用的子进程 stderr/stdout 合并方法，按子进程退出码判断，并保留完整输出；不要以关闭错误处理的方式掩盖真正失败。另将 Node 测试回执统一落盘，方便核对整次结果。

**完成标准：** 正常进度不会误报；合成失败和真实非零退出仍能让包装器失败；在实际支持的 PowerShell 环境分别验证。
