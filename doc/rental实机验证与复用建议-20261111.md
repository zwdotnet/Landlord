# rental 实机验证与复用建议

日期为 2026-11-11，时区为 Asia/Hong_Kong。

状态为本地候选评估完成。实际运行官方 Windows 发行包，抽查源码并构建前端。当前项目的业务代码实施、手机真机验收与发布仍待开展。

## 本次结论

建议采用 rental 作为改造起点，复用账号、房东台账权限、管理界面、租客门户和部分打印组件，同时调整租约、账单、收款与合同文件的关联模型。

本次发现已经涉及租赁核心数据关系，仅增加小程序、PWA 和 PDF 转换无法解决。考虑到已确认的自用规模，继续在现有 Go + Vue 工程中改造，比为了本次发现立刻切换大型平台基座更合适。这是本轮工程建议，性能与长期运维容量尚未实测。

这些选择只确定了上述范围。收据的触发时点、提醒渠道、合同费用细则等尚待决定。

## 需要调整的实现

### F01 同名租客可能读取前任账单

实际构造两个独立租客档案，姓名相同，入住先后不重叠但发生在同一个月。前任先开账单并退租，后任注册并绑定新档案后，列表和详情仍返回前任账单。

当前账单没有明确租约关联，租客门户通过房间、姓名子串与入住月份筛选。姓名与月份不足以唯一标识一次承租关系。建议账单绑定明确的 `lease_id`，门户沿登录账号绑定的租客及其授权租约查账；多人共同承租时显式记录成员。

证据为 `api-results.json` 中两项 same_name 断言及 `api-transcript.jsonl`。相关实现位于 `server/rental/tenant_portal.go` 的 `applyPortalBillScope`，约第 201 行。

### F02 提前续租调价立即影响旧租期

原租期至 2027-09-30、月租 2,000。评估日提前续一年并设新租金 2,500，随后创建 2026-12 账单，租金直接变为 2,500。

源码将续租新租金立即写入房间默认月租。建议为续签建立明确起止日期和费用条款版本，按账单覆盖区间读取对应版本，避免通过当前房间默认值推导所有期间费用。

证据为 `renewal-api.json` 与 `future_renewal_does_not_change_old_term_rent`。相关实现位于 `server/rental/renew.go`，约第 251 行。

另观察到该样本续一年后到期日变为 2028-09-29。当前算法把原到期日作为新租期基准再减一天。正式需求应先确定日期是否含首尾，随后覆盖月底和闰年边界。

### F03 房间与月份唯一约束限制换租客结算

系统拒绝同房同月的第二张账单，前后两个租约无法分别出账。建议围绕租约、收费期间和收费项建立账单唯一性，房间继续作为关联实体。切换租客当天的水电底数和结算边界需随交接记录保存。

证据为 `same_month_new_tenancy_bill_supported`。相关校验位于 `server/rental/bills.go`，约第 627 行；历史迁移中的唯一索引也需一并核查，不能只修改接口查重。

### F04 独立抄表台账与出账读数未连通

使用正式抄表接口录入本期读数后，再调用建账接口，账单取初始读数并将本期用量置零。检查前端集中抄表入口，也主要从账单和房间底数读取信息。

建议将账单费用与被采用的抄表记录明确关联。新增、修正、换表和补录需要有可追溯行为，生成账单时保存读数与费率快照。

证据为 `separate_meter_reading_used_in_bill`。相关实现位于 `server/rental/bills.go` 中的 `prefillReadings` 与 `newBillFromRoom`，以及 `web/src/components/MeterReadingModal.vue` 中的 `loadReadingData`。

### F05 合同正文随当前资料变化

续租后重新打开房屋租赁合同，显示原入住日期至延长后的到期日，并采用新租金。租期和价格直接读取当前租客与房间字段，无法据此恢复原合同正文。

建议签订时固化模板版本、填写数据和生成文件。续签创建新版本或协议，已归档合同继续引用签订时内容。

证据为 `contract-preview.txt`、`contract-browser-print.pdf` 和 `renewal-preview.txt`。相关实现位于 `web/src/components/ContractPrintModal.vue`，约第 223 行。

### F06 定时处理缺少目标业务链

本次检索到的 5 个调度任务分别涉及日志清理、备份、导出、08 点缴费汇总和 QQ 网关维护。没有找到合同约定的独立抄表计划或自动建账任务。

缴费通知实现注明失败当日不重试，调度器按下一个时间点重新计时。本轮未跨自然提醒周期验证消息实际送达，也没有因缺少抄表计划而伪造计划变更与补发的通过结果。

建议增加可持久化任务与结果，在重启后识别未完成任务，按业务唯一键防重复。使用现有 SQLite 承载初期任务状态即可作为待验证方案，暂不据此引入额外队列服务。

相关实现位于 `server/rental/notify_dispatch.go`、`server/scheduler/scheduler.go` 及调度任务注册处。

这份顺序是实施建议。本轮尚未开展上述产品改造，也未设定交付日期或自动安排后续任务。
