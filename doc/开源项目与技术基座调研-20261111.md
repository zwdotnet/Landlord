# 房东管理平台：开源项目、技术基座与组件调研

核对日期：2026-11-11，Asia/Hong_Kong。

状态为初版开源选型调研。2026-11-11 已继续对 rental 做本地运行、接口、前端构建和打印评估，新增事实与复用建议见 [rental 实机验证与复用建议](rental实机验证与复用建议-20261111.md)。下文的未实测与待选择描述保留为初版调研时的证据口径。

本轮范围来自用户要求：先寻找适合房东、租客、平台管理员使用，并覆盖 Web、WebApp、微信小程序的开源项目、基座与组件。本文件是当前调研记录，不是已确认的完整需求或实施计划。

## 结论与建议

有值得复用的项目。本次检索及抽查范围内，尚未确认一套可以直接覆盖全部要求、源码交付完整且无需改造的成品。

建议首先验证 **TechFunWay/rental**，它与收租、抄表、租客只读门户的业务最接近，而且公开许可证为 MIT。2026-10-20 发布的 **v0.7.1 是预览版**，新增续租、内置租赁合同与续租协议打印，不能仅看较早的 README 就判定它没有合同生成能力。[S01][S02][S03]

保留两条路线：

| 路线 | 适用判断 | 可复用内容 | 主要代价 |
|---|---|---|---|
| A：在 rental 上扩展 | 希望较快实现日常租赁管理，现有台账与计费模型能匹配业务 | 三种角色、房屋与租客、抄表、收费项目、收款、租客门户、模板打印 | 增补微信小程序、WebApp 能力；核对自动出账与抄表提醒；按需要补服务端 PDF 和模板版本 |
| B：通用平台基座 + 自有租赁模块 | 面向多房东长期运营，权限、合同规则、账务模型需要较多定制 | 优先考察芋道的账号、权限、多租户、文件与任务能力 | 租赁领域模型和界面需要自行实现；平台基座有更多运行依赖 |

这是调研建议，用户尚未选择路线。推荐先用代表性业务验证路线 A 的适配程度，再决定是否承担路线 B 的开发量，不凭功能数量或 Star 数直接定技术栈。

## 可复用成品

### 1. TechFunWay/rental：优先验证

技术组合为 Go、Gin、GORM、SQLite，前端 Vue 3、TypeScript、Vite。公开仓库提供 Docker 与多平台产物。[S01]

最贴近需求的部分是三层角色、按台账组织数据、租客个人门户、读数与计费、收款和收费单据。v0.7.1 又增加续租记录、内置合同/续租协议填充及 A4 打印。[S01][S02]

| 用户需求 | 当前证据 | 仍需补充或验证 |
|---|---|---|
| 房屋、租客与状态 | 文档覆盖；可见对应业务源码 | 退租与账期交界、同房换租客等实际行为 |
| 三种角色 | README 明确；`access.go` 有按台账及模块的权限逻辑 | 不能据此认定所有接口都已通过跨房东、跨租客隔离验证 |
| 新合同与续租 | v0.7.1 发行说明；`lease.ts` 有租期与续租计算 | 历史条款是否形成不可变快照，续签是否满足用户的合同流程 |
| 模板合同打印 | v0.7.1 内置房屋租赁合同/续租协议 | 用户模板能否上传或编辑；不能把内置模板当成任意 Word 模板系统 |
| PDF | 有浏览器打印路径及上传 PDF 存档 | 不能据此承诺服务端自动生成、永久归档、各端下载同一份 PDF |

| 收据 | 收费单据、打印、收款记录 | 应缴通知、收费单与实收凭证的业务口径要分清 |
| 租客门户 | 文档提供本人资料、合同、账单与缴费展示 | 换租客、同名租客、历史账单归属需验证 |

| 微信小程序 | 本轮未获得现成小程序实现证据 | 预计需要新增独立客户端和微信登录适配 |

已抽查代码：

- `server/rental/contracts.go`：这里的 `Contract` 是租客名下的附件实体，负责上传、预览、下载与归属校验；不能将此文件当成完整结构化租约模型。

版本核对补充：6.0.0 的重大更新明确写移除多租户。该项目仍值得参考，但不能不区分版本就当作现成多房东隔离底座；仓库简介与具体版本的发行说明应分别核对。[S27]

工程建议：

- 首期只选一个后端基座，不把两个后台框架拼接起来。
- 平台后台可以独立优化桌面表格体验，房东与租客移动端共享 API 和业务规则。
- 框架中的“多租户 tenant”通常表示数据隔离单元；本项目的“租客”是承租人。建议内部使用 `organization/landlord` 和 `renter` 等明确命名，避免混淆。
- 现有 Vue Web 界面不能因选用 uni-app 就视为可直接编译成小程序；应评估可复用的数据与逻辑，以及需要重新实现的页面。

这些是建议工程方式，尚未成为最终技术决定。

| Word 合同模板填充 | poi-tl | Apache 2.0；Java 的 DOCX 模板渲染 | 适合 Java 路线与现有 Word 模板；输出 DOCX 后仍需 PDF 转换步骤。[S24] |
| WebApp/PWA | vite-plugin-pwa | MIT；Vite 的 PWA 插件 | 负责应用清单、Service Worker 等；提醒订阅、发送和手机端实际到达需要另做。[S25] |
| Go 异步任务、重试 | Asynq | MIT；Redis 支持的 Go 任务队列，提供计划任务、失败重试与恢复 | 会引入 Redis；业务侧仍须实现重复执行不重复出账、不重复发收据。[S26] |
| Java 任务调度 | 基座内的 SnailJob 等 | RuoYi-Vue-Plus 已集成调度与重试能力 | 先复用选定基座；不为同一用途同时引入多套调度器。[S18] |

建议的合同生成流程是：

`选择模板版本 → 读取本次合同数据快照 → 填充模板 → 生成 PDF → 保存文件与归属 → 房东/租客按权限查看或打印`

若模板固定且由平台维护，可优先验证 HTML 模板 + Gotenberg。若必须兼容房东上传的 Word 模板，则另评估 DOCX 填充方案。pdfme 适合需要可视化模板编辑的场景，不必在第一期同时引入所有方案。

“浏览器另存为 PDF”和“服务器生成并保存 PDF”应分别验收。前者可以满足部分人工打印流程，后者更适合各端查看同一份历史合同。

## 需要防止误判的业务缺口

以下是针对本需求提出的设计与验证要求，不是断言所有候选均有这些缺陷。

1. **合同不能只存文件。** 租金、押金、租期、支付周期、抄表周期、提前天数要能参与业务计算；签约时文本及费用条件建议保留快照。
2. **催缴不等于抄表提醒。** 前者通常提醒租客付款，后者提醒房东或抄表人录入读数；时间和接收对象可能不同。
3. **一键出账不等于自动出账。** 需要明确无人登录时是否触发；读数未齐时生成待补充账单还是暂缓水电费用，需要用户规则。
4. **应付金额不等于已收款。** 建议待付款输出缴费通知，确认收款后输出对应金额的收款收据。用户使用“收据”的具体含义尚待确认。
5. **多个账号不等于完整隔离。** 房东 A 不能通过编号、下载地址、导出接口看到房东 B 的数据；租客也只能访问本人范围。
6. **续租不能只覆盖日期。** 新旧合同条款、租金生效时间、历史账单以及协议版本之间要有可追溯关系。
7. **有定时器不等于可靠提醒。** 建议保存应执行任务、重试和结果；提醒渠道未确定前不能承诺微信或浏览器通知稳定送达。

本轮未核实本项目可用的微信订阅消息类目、长期订阅资格或通知到达率。这些条件在选择提醒渠道时核实。

## 建议的后续最小验证

本节为待执行建议，不表示已经授权安装、已经安排任务或已经通过测试。

优先对 rental 的固定提交建立隔离验证环境，用两名房东和各自租客走完：

1. 建房、入住、填写月付/季付租约与独立水电周期。
2. 按内置模板生成/打印合同，使用长姓名、多页条款和中文检查输出；确认服务端 PDF 的缺口。
3. 录入两期水电读数，生成账单，比较预期金额；重复触发不能重复计费。
4. 记录部分收款和结清，检查单据与实收金额是否一致。
5. 续租并调整未来租金，确认已出历史账单不被改写。
6. 分别以两个房东、两个租客访问详情、文件和导出，验证数据隔离。
7. 修改抄表计划并模拟服务重启，检查是否漏任务或重复提醒。

建议继续复用的条件：现有模型能承接上述流程，缺口集中在 PDF、提醒和多端适配。

建议转向通用基座的条件：为支持合同历史、跨房东权限、租客归属和账期规则，需要同时重写核心数据与大部分业务入口。届时应比较改造量后再决定，不能仅凭本轮文档阅读断言需要重写。

## 留待需求访谈的关键问题

| 待定事项 | 影响 | 最迟处理阶段 |
|---|---|---|
| 面向个人/少数熟悉房东，还是公开入驻运营；预计房东和房间规模 | 数据隔离单元、运维方式、是否值得采用较重平台基座 | 确定路线前 |
| WebApp 是手机网页，还是可安装 PWA；是否必须有系统通知 | 客户端工作量和提醒方式 | 客户端选型前 |
| 合同模板由平台维护，还是房东上传 Word/PDF 并自行编辑 | 模板引擎、PDF 方案、版本与编辑界面 | 合同模块设计前 |
| 提前提醒的接收人、渠道、周期与天数 | 任务数据、订阅关系、渠道依赖 | 提醒模块设计前 |
| 只记录线下收款，还是接入在线支付；“收据”对应应付还是实收 | 账务状态、单据触发与支付接入 | 账务模块设计前 |

当前没有确定部署主机、固定端口、数据库最终选型或上线时间。没有引用其他项目的历史部署作为本项目约束。
